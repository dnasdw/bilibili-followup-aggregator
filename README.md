# B站关注动态聚合器（bilibili-followup-aggregator）

一个 Tampermonkey 用户脚本：聚合 B 站**全部关注 UP 主**的视频动态（正式投稿 + 动态视频），按发布时间重建完整时间线，**绕过 B 站关注动态页只能回看约 75 天历史的限制**——可以从任意日期回溯补课，一路扫到每个 UP 主发布的第一条内容；追番追剧、订阅合集一并入库，联合投稿自动识别主UP主。

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

## 它解决什么问题

- B 站动态页（`t.bilibili.com`）只能从最新往旧滚动加载，**无法跳转到指定日期**；
- 关注动态流接口在服务端只保留约 **75 天**历史，浏览器翻不动了不是你的问题，是接口不给了；
- 长时间没刷动态想"补课"？官方页面没有任何办法。

本脚本逐个拉取每位关注 UP 主的**空间动态流**（该接口无 75 天限制），并同步追番/追剧与订阅合集的全部剧集，在本地聚合成一条按时间排序的完整时间线，装进浏览器里的一个面板。

## 功能特性

| 特性 | 说明 |
|---|---|
| 🗓 **全量补课** | 指定起始日期回溯；把日期设到 2000 年即"真·全量"——扫到每个 UP 的第一条动态 |
| ➕ **增量更新** | 每个 UP / 每个合集独立记录上次扫描时间，日常一次增量只需几分钟 |
| 🆕 **新关注/新订阅自动补全** | 新关注的 UP、新订阅的合集在下一次增量更新时自动扫完全部历史 |
| 📺 **追番追剧** | 基于你的追番/追剧列表逐部拉取全部剧集（番剧/电影/纪录片/国创/电视剧/综艺），无历史深度限制，新追的剧自动补全 |
| 📚 **订阅合集** | 自动同步"我追的"订阅合集（含 App 端订阅），合集分集进时间线；取消订阅自动清理 |
| 🔖 **分类标签页** | 全部视频 / 视频投稿 / 追番追剧 / 订阅合集 四个分类页，独立页码与记忆 |
| 🏷 **特殊类型标注** | 充电专属、直播回放、合作视频等自动识别并以标签区分显示 |
| 🤝 **合作视频主UP识别** | 联合投稿会同时出现在所有参与者的空间动态里——脚本在发现同一视频挂到两个UP名下时，自动查询视频详情接口，把归属修正为**发布稿件的主UP主**（`owner`），卡片上以"合作 +N"标注全部参与者（悬停可见各自分工）；只关注参演者时仍归属该参演者，不浪费请求 |
| 🧹 **取关/退订清理** | 可选：取消关注 UP / 取消订阅合集 / 取消追番追剧时自动移除对应记录；交叉来源的视频仅移出对应分类页，全部来源移除后才删除本地记录；联合投稿只要主 UP 或任一合作者仍被关注即保留 |
| ⚙ **设置面板** | 默认分类页、清理策略可配置，设置随数据一起导出/导入 |
| 🃏 **卡片式浏览** | 封面 / 头像 / 标题 / 精确到分的时间 / 时长，首页·尾页·±10页·跳页·键盘翻页·页码记忆·浏览位置锚定 |
| 📦 **导出 / 导入** | JSON 一键导出，迁移电脑时合并式导入（不覆盖现有数据） |
| 🛡 **风控对策** | 内置 wbi 签名（官方测试向量验证）、请求节流、-352 长退避自动重试、后台标签页不暂停（Web Worker 计时） |

## 安装

1. 浏览器安装 [Tampermonkey](https://www.tampermonkey.net/) 扩展；
2. 任选一种方式安装脚本：
   - **Greasyfork（推荐，自动更新）**：[点此安装](https://greasyfork.org/scripts/596673)
   - **GitHub 直装**：打开 [bilibili-followup-aggregator.user.js](bilibili-followup-aggregator.user.js) 的 raw 文件，Tampermonkey 会弹出安装界面；
3. 打开 [t.bilibili.com](https://t.bilibili.com/)，页面右下角出现 📺 按钮即安装成功。

## 使用

**第一次（补历史课）：**

1. 点 📺 打开面板，"起始日期"设为你想回到的日期（想扫全部就设到 2000-01-01）；
2. 点 **全量补课**，脚本自动拉取关注列表并逐 UP 扫描——关注多、UP 高产时耗时较长（可能数小时），支持随时中断与续扫；
3. 完成后时间线即可浏览：点击条目直达视频页。

**日常（保持不断档）：**

- 每隔几天点一次 **增量更新**（通常几分钟），新内容自动并入时间线；
- 新关注的 UP 无需任何操作，增量更新会自动补全其全部历史。

**迁移电脑：**

旧电脑 **导出 JSON** → 新电脑装好脚本并登录 B 站 → **导入 JSON** → 继续增量。

## 工作原理

```
你的登录态（cookie，仅请求 B 站官方 API）
  ├─ ① nav 接口            → 你的 uid + wbi 签名密钥
  ├─ ② 关注列表接口（wbi 签名）→ 全部关注 → 逐 UP 空间动态流（无历史限制）
  ├─ ③ "我追的"列表         → 订阅合集 → 逐合集分集列表（无历史限制）
  ├─ ④ 追番/追剧列表        → 逐部剧集详情，全部集数入库（无历史限制）
  └─ ⑤ 本地合并（按 id 去重 + 来源标签；联合投稿归属冲突时查视频详情接口修正为主UP）→ 分类时间线 → 面板浏览
```

- **为什么扫空间动态而不是关注动态流**：关注流有约 75 天服务端限制，空间动态流没有；
- **为什么能同时收到投稿视频和动态视频**：两者在动态体系中是同一类型（`DYNAMIC_TYPE_AV`），都带可正常播放的 bvid；
- **订阅合集的识别**：web 端"我追的"列表混合了合集与收藏夹，脚本逐个试探性调用合集接口，仅跟踪真正的合集；
- **来源标签机制**：每条记录带来源标签（关注/订阅合集/追番），同一视频从多个渠道扫到时标签合并——分类页、取关清理都由标签驱动；
- **合作视频归属**：B站联合投稿由主投UP上传稿件、同步出现在全部成员的空间动态中，动态流接口本身不区分主次。脚本采用"冲突触发式查询"：同一视频仅从一个UP扫到时归属该UP（无论主次，不耗额外请求）；从**两个及以上**UP扫到时查询视频详情接口（`owner` 即主UP），修正归属、记录完整 staff 名单并打上已验证标记。历史错记数据重跑全量补课即可自愈；取关主UP但仍有合作者被关注时，视频保留；
- **wbi 签名**：关注列表等接口要求 wbi 签名，脚本内置标准算法（含 md5 实现，零外部依赖，通过 [bilibili-API-collect](https://github.com/SocialSisterYi/bilibili-API-collect) 官方测试向量验证）；
- **风控**：请求随机节流（1.2~2.4s）；风控码（-352 等）自动刷新密钥并长退避重试；优先使用页面级 `fetch` 保持浏览器请求指纹；
- **后台不暂停**：计时走 Web Worker（不受后台标签页定时器节流影响），切到其他页面扫描照常进行。

## 数据与隐私

- 所有数据仅保存在**本地浏览器**（Tampermonkey 存储），不上传任何服务器；
- 网络请求只发往 `api.bilibili.com`（`@connect` 已声明，可自行检查）；
- 无外部脚本依赖（`@require` 为零）、无代码混淆、无统计上报；
- 随时可导出全部数据或一键清空。

## 已知限制

- 充电专属视频的可见性取决于你的账号权限（未充电的 UP 的充电专属内容仍不可见）；
- UP 主**转发**他人视频的动态不收录（仅收录 UP 自己发布的视频内容）；
- 合集与收藏夹在"我追的"列表中混合返回，脚本靠试探调用区分，个别条目可能识别不准；
- 脚本依赖 B 站 web 端接口，B 站改版后可能需要更新适配；
- 短时间内高频扫描任何 B 站接口都有触发风控的可能，脚本已内置节流与退避，但请避免多工具同时高频抓取。

## FAQ

**问：全量补课为什么这么慢？**
空间动态接口每页仅 12 条且必须顺序翻页，UP 越多、越高产耗时越长。这是接口机制决定的，脚本已按风控安全上限速度请求。扫描可中断、可续扫，分几天跑完也没问题。

**问：日志里出现 `-352` 怎么办？**
偶发的 `-352` 是风控拦截，脚本会自动长退避（20s 起指数递增）并刷新签名后重试，通常能自愈。只有连续重试失败导致扫描中断时才需要稍后再"继续未完成的扫描"。

**问：增量更新会把新 UP 扫到多久之前？**
新关注的 UP 会被完整扫到它自己的第一条动态；已扫过的 UP 只补上次扫描以来的新内容，速度很快。

**问：能把起始日期改早重新补课吗？**
可以。改早日期重跑全量即可，已有数据按 bvid 去重合并，不会重复也不会丢失。

**问：合作视频的归属错了怎么办？**
联合投稿的归属以视频详情接口的发布账号（主UP）为准。若早期数据记错了归属，把起始日期设早重跑一次全量补课即可自愈：同一视频再次从多个 UP 的空间扫到时会自动查询并修正。

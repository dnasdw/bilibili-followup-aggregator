# B站关注动态聚合器（bilibili-followup-aggregator）

一个 Tampermonkey 用户脚本：聚合 B 站**全部关注 UP 主**的视频动态（正式投稿 + 动态视频），按发布时间重建完整时间线，**绕过 B 站关注动态页只能回看约 75 天历史的限制**——可以从任意日期回溯补课，一路扫到每个 UP 主发布的第一条内容。

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

## 它解决什么问题

- B 站动态页（`t.bilibili.com`）只能从最新往旧滚动加载，**无法跳转到指定日期**；
- 关注动态流接口在服务端只保留约 **75 天**历史，浏览器翻不动了不是你的问题，是接口不给了；
- 长时间没刷动态想"补课"？官方页面没有任何办法。

本脚本逐个拉取每位关注 UP 主的**空间动态流**（该接口无 75 天限制），在本地聚合成一条按时间排序的完整时间线，装进浏览器里的一个面板。

## 功能特性

| 特性 | 说明 |
|---|---|
| 🗓 **全量补课** | 指定起始日期回溯；把日期设到 2000 年即"真·全量"——扫到每个 UP 的第一条动态 |
| ➕ **增量更新** | 每个 UP 独立记录上次扫描时间，日常一次增量只需几分钟 |
| 🆕 **新关注自动补全** | 新关注的 UP 在下一次增量更新时自动扫完全部历史 |
| ⏸ **断点续扫** | 每扫完一个 UP 即存档，中断后从断点继续 |
| 🎬 **动态视频也收** | 投稿视频 + 动态视频统一收录（条目带标签区分） |
| 🃏 **卡片式浏览** | 封面 / UP 头像 / 标题 / 精确到分的时间 / 时长，首页·尾页·±10页·跳页·键盘翻页·页码记忆 |
| 📦 **导出 / 导入** | JSON 一键导出，迁移电脑时合并式导入（不覆盖现有数据） |
| 🛡 **风控对策** | 内置 wbi 签名（官方测试向量验证）、请求节流、-352 长退避自动重试 |

## 安装

1. 浏览器安装 [Tampermonkey](https://www.tampermonkey.net/) 扩展；
2. 任选一种方式安装脚本：
   - **Greasyfork（推荐，自动更新）**：[点此安装](https://greasyfork.org/) *(链接待发布后更新)*
   - **GitHub 直装**：打开 [bilibili-followup-aggregator.user.js](bilibili-followup-aggregator.user.js) 的 raw 文件，Tampermonkey 会弹出安装界面；
3. 打开 [t.bilibili.com](https://t.bilibili.com/)，页面右下角出现 📺 按钮即安装成功。

## 使用

**第一次（补历史课）：**

1. 点 📺 打开面板，"起始日期"设为你想回到的日期（想扫全部就设到 2000-01-01）；
2. 点 **全量补课**，脚本自动拉取关注列表并逐 UP 扫描——关注多、UP 高产时耗时较长（可能数小时），支持随时中断与续扫；
3. 完成后时间线即可浏览：点击条目直达视频页。

**日常（保持不断档）：**

- 每隔几天点一次 **增量更新**（通常几分钟），新内容自动并入时间线；
- 新关注的 UP 无需任何操作，增量更新会自动补全其全部历史。

**迁移电脑：**

旧电脑 **导出 JSON** → 新电脑装好脚本并登录 B 站 → **导入 JSON** → 继续增量。

## 工作原理

```
你的登录态（cookie，仅请求 B 站官方 API）
  ├─ ① nav 接口            → 你的 uid + wbi 签名密钥
  ├─ ② 关注列表接口（wbi 签名）→ 全部关注
  ├─ ③ 每位 UP 的空间动态流   → 过滤视频类动态（DYNAMIC_TYPE_AV），
  │                           翻页至目标日期/最早动态为止
  └─ ④ 本地合并（bvid 去重）  → 按时间排序的时间线 → 面板浏览
```

- **为什么扫空间动态而不是关注动态流**：关注流有约 75 天服务端限制，空间动态流没有；
- **为什么能同时收到投稿视频和动态视频**：两者在动态体系中是同一类型（`DYNAMIC_TYPE_AV`），都带可正常播放的 bvid；
- **wbi 签名**：关注列表等接口要求 wbi 签名，脚本内置标准算法（含 md5 实现，零外部依赖，通过 [bilibili-API-collect](https://github.com/SocialSisterYi/bilibili-API-collect) 官方测试向量验证）；
- **风控**：请求随机节流（1.2~2.4s）；风控码（-352 等）自动刷新密钥并长退避重试；优先使用页面级 `fetch` 保持浏览器请求指纹。

## 数据与隐私

- 所有数据仅保存在**本地浏览器**（Tampermonkey 存储），不上传任何服务器；
- 网络请求只发往 `api.bilibili.com`（`@connect` 已声明，可自行检查）；
- 无外部脚本依赖（`@require` 为零）、无代码混淆、无统计上报；
- 随时可导出全部数据或一键清空。

## 已知限制

- **充电专属 / 会员专属视频**不在公开接口中，无法收录；
- UP 主**转发**他人视频的动态不收录（仅收录 UP 自己发布的视频内容）；
- 脚本依赖 B 站 web 端接口，B 站改版后可能需要更新适配；
- 短时间内高频扫描任何 B 站接口都有触发风控的可能，脚本已内置节流与退避，但请避免多工具同时高频抓取。

## FAQ

**问：全量补课为什么这么慢？**
空间动态接口每页仅 12 条且必须顺序翻页，UP 越多、越高产耗时越长。这是接口机制决定的，脚本已按风控安全上限速度请求。扫描可中断、可续扫，分几天跑完也没问题。

**问：日志里出现 `-352` 怎么办？**
偶发的 `-352` 是风控拦截，脚本会自动长退避（20s 起指数递增）并刷新签名后重试，通常能自愈。只有连续重试失败导致扫描中断时才需要稍后再"继续未完成的扫描"。

**问：增量更新会把新 UP 扫到多久之前？**
新关注的 UP 会被完整扫到它自己的第一条动态；已扫过的 UP 只补上次扫描以来的新内容，速度很快。

**问：能把起始日期改早重新补课吗？**
可以。改早日期重跑全量即可，已有数据按 bvid 去重合并，不会重复也不会丢失。
